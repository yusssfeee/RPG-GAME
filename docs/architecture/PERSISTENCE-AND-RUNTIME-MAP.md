## Migration risks

1. Save compatibility: changing state shape or serialization can make existing player saves unreadable.
2. Slot compatibility: the legacy `tinyacre-save` mirror is a compatibility path; do not remove it until a verified migration plan exists.
3. Save timing: mining state is synchronized before serialization; extracting mining without preserving this ordering could lose progress.
4. Silent failures: several storage operations are wrapped in try/catch. Future diagnostics should improve observability without changing current behavior in the first extraction.
5. Runtime globals: save/load functions depend on shared state and helpers; move them only after their dependencies are explicit.
6. Event lifecycle: global listeners and page lifecycle events can be duplicated if modules initialize more than once.

## Safe future approach

- Treat the current serialized campaign as a versioned external contract, even if it currently has no explicit version field.
- First add characterization tests around save -> reload -> state equality using disposable copies of saves.
- Preserve all existing keys and slot fallback behavior during the first modular releases.
- Add any future save schema versioning as a backward-compatible layer; do not rewrite existing saves in place without a backup.
- Keep a single persistence owner/service in the eventual architecture. Gameplay modules should request save/load operations rather than writing arbitrary storage keys.
- Do not change persistence implementation during Phase 0.
